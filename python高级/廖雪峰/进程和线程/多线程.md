多线程跟多进程最大的区别就一句话：**多进程内存互相隔离，多线程共享同一块内存**。这个区别既是多线程灵活的地方，也是它所有麻烦的根源。咱们按“怎么开线程 → 共享变量会出什么事 → 加锁 → GIL 限制 → ThreadLocal → 到底什么时候用”这条线走。

# 多线程 · 笔记

## 先分清：线程和进程差在哪

进程是操作系统分配资源的单位，**每个进程有自己独立的内存空间**。线程是操作系统调度的单位，**一个进程内的所有线程共享同一块内存**。你前面学多进程时见过“子进程改个全局变量，父进程看不见”，到了多线程这里，**任何一个线程改了全局变量，其他线程立刻看得见**。

Python 的线程是**真正的操作系统线程**（Posix Thread），不是模拟的。标准库有两个模块：`_thread` 和 `threading`，`threading` 是高级封装，**日常只用 `threading`**。

---

## 开一个线程：跟 Process 几乎一样

```python
import time, threading                          # 导入 time 和 threading

def loop():                                     # 线程要执行的函数
    print('线程 %s 启动' % threading.current_thread().name)   # current_thread() 拿当前线程对象
    n = 0
    while n < 5:
        n += 1
        print('线程 %s >>> %s' % (threading.current_thread().name, n))
        time.sleep(1)                           # 模拟耗时操作
    print('线程 %s 结束' % threading.current_thread().name)

print('主线程 %s 启动' % threading.current_thread().name)   # 任何进程默认有一个主线程，名字叫 MainThread
t = threading.Thread(target=loop, name='LoopThread')   # 创建 Thread，target 是函数，name 是线程名
t.start()                                       # 启动线程
t.join()                                        # 主线程等待子线程结束
print('主线程 %s 结束' % threading.current_thread().name)
```

**跟 `Process` 的对应关系**：`Thread(target=函数)` 对应 `Process(target=函数)`，`start()` 启动，`join()` 等待，逻辑一模一样。区别在于 `Thread` 多了一个 `name` 参数，**名字只用于打印显示，没有功能意义**，不起名就自动叫 `Thread-1`、`Thread-2`。

## 坑一：多线程共享变量，不加锁会被改乱

这是多线程最核心的问题，原文用银行存款的例子讲得很清楚。

```python
balance = 0                                     # 全局共享变量，所有线程都能改

def change_it(n):                               # 先存后取，理论上结果应始终为 0
    global balance
    balance = balance + n                       # 存入 n
    balance = balance - n                       # 取出 n

def run_thread(n):
    for i in range(1000000):                    # 反复执行，制造线程切换的机会
        change_it(n)

t1 = threading.Thread(target=run_thread, args=(5,))
t2 = threading.Thread(target=run_thread, args=(8,))
t1.start(); t2.start()                          # 两个线程同时跑
t1.join(); t2.join()
print(balance)                                  # 结果不一定为 0，可能是 -3、5、-8 等任何值
```

**为什么不是 0？** 因为 `balance = balance + n` 这一行在 CPU 层面**不是一条指令，而是多条**：先读 `balance`，算加法，再写回 `balance`。两个线程交替执行时，可能发生这种事：

1. t1 读到 `balance = 0`，算出 `0 + 5 = 5`，**还没来得及写回**；
2. 操作系统切到 t2，t2 读到 `balance = 0`，算出 `0 + 8 = 8`，**写回 `balance = 8`**；
3. 切回 t1，t1 把自己刚才算的 `5` **写回 `balance`**，覆盖掉了 t2 的结果。

两个线程各读各的、各写各的，**中间任何一步被打断，最终结果就不对**。这叫**竞态条件**（race condition）。

---

## 加锁：`threading.Lock`

要保证“一个线程在修改 `balance` 时，其他线程不能插进来”，就得给这段代码**上锁**。

```python
import threading

balance = 0
lock = threading.Lock()                         # 创建一个锁对象，全局唯一

def change_it(n):
    global balance
    balance = balance + n
    balance = balance - n

def run_thread(n):
    for i in range(100000):
        lock.acquire()                          # 获取锁，拿不到就阻塞等待
        try:
            change_it(n)                        # 被锁保护的“临界区”，同一时刻只有一个线程能进
        finally:
            lock.release()                      # 无论是否出错，一定要释放锁
```

**`acquire()` 和 `release()` 必须成对出现**。用 `try...finally` 是为了确保**即使 `change_it` 里抛了异常，锁也会被释放**。忘了 `release()`，其他线程会永远卡在 `acquire()` 上，变成“死线程”。

更简洁的写法是用 `with`：

```python
def run_thread(n):
    for i in range(100000):
        with lock:                              # 进入 with 自动 acquire，离开自动 release，异常也不会漏
            change_it(n)
```

**锁的代价**：被锁保护的代码**只能串行执行**，多线程的并发优势在这段代码上完全消失，效率下降。此外，**多个锁使用不当会造成死锁**：两个线程各持一把锁，又都在等对方的锁，双方永远挂起。

## GIL：Python 多线程的“天花板”

加锁能保证正确性，但 Python 多线程还有一个更根本的限制：**GIL（全局解释器锁）**。

原文的实测很直观：在 4 核 CPU 上启动 4 个死循环线程，**CPU 占用只有 102% 左右，只跑满了一个核**。用 C/C++ 或 Java 写同样的代码，4 核能跑到 400%。

原因在于：**任何 Python 线程在执行字节码之前，必须先获得 GIL；每执行 100 条字节码，解释器就自动释放 GIL，让其他线程有机会跑**。这意味着**同一时刻只有一个线程在执行 Python 代码**，多线程在 Python 里只能“交替执行”，即使你有 100 个线程跑在 100 核上，**也只能用到 1 个核**。

GIL 是 CPython 解释器的**历史设计遗留**，短时间内不会消失。想真正利用多核，要么用**多进程**（每个进程有独立的 GIL，互不影响），要么用 C 扩展绕过。

---

## 那 Python 多线程到底还有什么用

答案很明确：**I/O 密集型任务**。

GIL 限制的是“**执行 Python 字节码**”这件事。当线程在等网络响应、等文件读写、等数据库返回时，它**不在执行字节码**，GIL 可以被其他线程拿走。所以在爬虫、文件处理、网络请求这类“大部分时间在等 I/O”的场景里，**多线程能显著提升吞吐量**，因为等待的时间被重叠利用了。

反过来，**CPU 密集型任务**（大量数学计算、图像处理、循环运算），GIL 让多线程完全发挥不了多核优势，**这种场景应该用多进程**。

一句话：**I/O 密集型用多线程，CPU 密集型用多进程**。

## ThreadLocal：每个线程一份独立副本

多线程共享变量会出问题，加锁是一种解法，但有时候你只是想让**每个线程各自拥有一份自己的数据**，互不干扰。这就是 `threading.local()` 的用途。

```python
import threading

local_school = threading.local()                # 创建一个 ThreadLocal 对象，全局只有这一个

def process_student():
    name = local_school.student                  # 每个线程读自己的 student 属性
    print('Hello, %s (in %s)' % (name, threading.current_thread().name))

def process_thread(name):
    local_school.student = name                  # 每个线程写自己的 student，互不影响
    process_student()

t1 = threading.Thread(target=process_thread, args=('Alice',), name='Thread-A')
t2 = threading.Thread(target=process_thread, args=('Bob',), name='Thread-B')
t1.start(); t2.start(); t1.join(); t2.join()
# 输出：Hello, Alice (in Thread-A) / Hello, Bob (in Thread-B)
```

`local_school` 是一个**全局对象**，但**每个线程对它属性的读写都是独立的副本**。线程 A 写 `local_school.student = 'Alice'`，线程 B 写 `'Bob'`，互相看不见。**内部自动处理了隔离，不需要你手动加锁**。

ThreadLocal 的典型用途是**在一个线程的多个函数之间传递数据**，比如每个请求一个线程，把用户信息存进 ThreadLocal，这个线程里任意函数都能读到，不用一层层传参数。

## 多进程 vs 多线程：一张表记住

| | 多进程 | 多线程 |
|---|---|---|
| 内存 | **隔离**，各自独立 | **共享**，任何线程可改任何变量 |
| 数据传递 | 需要 `Queue`、`Pipe` | 直接读写共享变量，但**必须加锁** |
| 多核利用 | **可以**，每个进程独立 GIL | **不行**，GIL 限制只能用一个核 |
| 适用场景 | **CPU 密集型** | **I/O 密集型** |
| 开销 | 创建进程重，切换慢 | 创建线程轻，切换快 |
| 主要风险 | 数据隔离，通信复杂 | 竞态条件、死锁 |
