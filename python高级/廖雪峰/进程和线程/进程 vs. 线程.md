这页是前面多进程、多线程两篇的总结对比课，核心就一件事：**把手里的任务，按对的维度选对并发模型**。

---

## 多任务的基本骨架：Master-Worker

原文开篇先定了讨论的前提。实现多任务，通常设计成 **Master-Worker 模式**：一个 Master 负责分配任务，多个 Worker 负责干活。

用多进程实现，主进程是 Master，子进程是 Worker；用多线程实现，主线程是 Master，子线程是 Worker。这个骨架本身不复杂，真正要选的是：**Worker 到底用进程还是线程来当。**

---

## 第一维：稳定性 vs 效率，进程和线程各让一步

先把多进程和多线程的硬优缺点摆出来。

**多进程最大的优点：稳定。** 一个子进程崩溃了，不影响主进程和其他子进程（当然主进程挂了全完，但 Master 只负责派活，挂的概率低）。Apache 最早采用的就是多进程模式。**缺点：创建代价大。** Unix/Linux 上用 `fork` 还行，Windows 下创建进程开销巨大；而且操作系统能同时跑的进程数有限，几千个进程同时运行，调度都成问题。

**多线程的硬伤：不稳定。** 任何一个线程挂掉，都可能把整个进程带走，因为所有线程共享同一块内存。Windows 上常见的“该程序执行了非法操作，即将关闭”，往往就是一个线程出了问题，操作系统强制结束了整个进程。

这个稳定性差异，在真实的 Web 服务器选型里直接体现出来了：**Windows 下多线程效率比多进程高，所以微软的 IIS 默认采用多线程模式；但多线程有稳定性问题，IIS 的稳定性就不如采用多进程的 Apache**。后来两边都搞出了“多进程 + 多线程”的混合模式，原文吐槽了一句“真是把问题越搞越复杂”。

---

## 第二维：别开太多，切换本身要花钱

原文用一个很直观的例子讲线程切换的开销：五科作业，每科一小时。单任务做完一科再做下一科，总共五小时；多任务模型每分钟切换一科，看起来像同时写五科，但**切换本身是有代价的**——收拾语文书本、找出数学圆规，这叫保存现场和准备新环境。

操作系统切换进程或线程也是一样：**保存当前 CPU 寄存器状态、内存页，再恢复新任务的执行环境**，这个过程虽然快，但要花时间。如果有几千个任务同时进行，操作系统可能**主要忙着切换，根本没多少时间真正执行任务**，表现就是硬盘狂响、点窗口无反应、系统假死。

**结论很硬：多任务数量一旦多到某个限度，消耗掉系统所有资源，效率急剧下降，所有任务都做不好**。不是开得越多越快，是开得越多越慢。

---

## 第三维：计算密集型 vs IO 密集型，这才是选型的核心

原文把任务分成两类，这是整页最值钱的判断标准。

**计算密集型**：大量计算，吃 CPU，比如算圆周率、高清视频解码。这类任务多任务反而拖后腿——任务越多，花在切换上的时间越多，CPU 干活的效率越低。**同时进行的数量应当等于 CPU 核心数**，多开无益。原文还有一句很直接的话：**Python 这种脚本语言运行效率很低，完全不适合计算密集型任务，这种活最好用 C 写**。

**IO 密集型**：涉及网络、磁盘 IO，**CPU 消耗很少，大部分时间都在等 IO 完成**（因为 IO 速度远低于 CPU 和内存）。这类任务**越多，CPU 效率越高，但也有上限**。原文指出一个关键事实：**常见的大部分任务都是 IO 密集型，比如 Web 应用**。

把这一维和前面的 GIL 串起来，选型逻辑就闭合了：计算密集型在 Python 里**该用多进程**，因为每个进程有独立的 GIL，能真正吃满多核；IO 密集型**多线程就够**，线程等 IO 时会释放 GIL，等待的时间可以被别的线程利用。原文还补了一刀：IO 密集型任务 99% 的时间花在 IO 上，用 C 替换 Python **几乎无法提升效率**，所以这类任务**首选开发效率最高的脚本语言**，C 反而是最差的选择。

---

## 第四维：异步 IO，单线程也能扛多任务

原文最后提了一个趋势性的方案。既然大部分任务都在等 IO，现代操作系统已经支持**异步 IO**，充分利用它，**单进程单线程就能执行多任务**，这叫**事件驱动模型**。Nginx 就是典型：单核 CPU 上单进程高效支持多任务，多核上就开和核心数相同的多个进程，操作系统调度非常高效。

对应到 Python，**单线程的异步编程模型就是协程**，后面会专门讲。这页只需要记住：**异步 IO / 协程是多任务选型里的第三个选项**，不是只有进程和线程两条路。

---

## 一张表收束整页

| 判断维度 | 多进程 | 多线程 | 异步 IO / 协程 |
|---|---|---|---|
| **稳定性** | **高**，子进程崩溃互不影响 | **低**，一线程崩全进程崩 | 单线程，无此问题 |
| **创建开销** | 大（Windows 尤其大） | 小 | 最小 |
| **多核利用** | **可以**，独立 GIL | **不行**，GIL 锁死单核 | 单线程，不涉及多核 |
| **最适合** | **计算密集型** | **IO 密集型** | **高并发 IO** |
| **数量上限** | 低（几百到几千） | 中 | 高（可上万连接） |

**一句话选型**：**计算密集型选多进程，普通 IO 密集型选多线程，高并发 IO 选异步 IO / 协程。** 稳定性优先且预算允许，多进程；效率优先且能接受崩溃风险，多线程；连接数极大、不想管线程切换，异步。
