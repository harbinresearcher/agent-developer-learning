# 单元测试 · 笔记

## 先聊一句：这东西到底在防什么

你现在写的代码，今天跑通了，不代表下个月改两行之后还通。单元测试就是**把你对代码行为的预期写下来，变成能自动跑的检查**。以后每次改完，跑一遍，没红就说明你没把原来的行为改坏。

原文对 `abs()` 的测试用例说得很清楚：正数、负数、0、非数值类型，各测一遍，这就是一个完整的单元测试。测试通过了，你就有了“重构的信心”；测试挂了，要么代码有 bug，要么测试条件写错了，总之你得修到它绿。

---

## 从例子入手：一个可以属性访问的 Dict

原文先写了一个 `Dict` 类，行为跟 `dict` 一样，但多一个能力：`d.a` 等价于 `d['a']`。

```python
class Dict(dict):
    def __init__(self, **kw):
        super().__init__(**kw)                  # 初始化父类 dict

    def __getattr__(self, key):                 # 点属性访问时触发
        try:
            return self[key]                    # 走 dict 的取键逻辑
        except KeyError:
            raise AttributeError(               # 键不存在时，转成属性错误
                r"'Dict' object has no attribute '%s'" % key
            )

    def __setattr__(self, key, value):          # 给点属性赋值时触发
        self[key] = value                       # 转成 dict 的赋值
```

这个类本身没什么难的，重点在于**它给了我们一个可以测试的目标**。下面所有单元测试的写法，都是围绕它展开的。

## unittest 的骨架：继承 TestCase，方法名以 test_ 开头

写单元测试，核心就三件事：

1. **导入 `unittest`**；
2. **写一个测试类，继承 `unittest.TestCase`**；
3. **每个测试方法都以 `test_` 开头**，不以 `test_` 开头的普通方法不会被当成测试执行。

```python
import unittest
from mydict import Dict

class TestDict(unittest.TestCase):

    def test_init(self):                        # 测初始化
        d = Dict(a=1, b='test')
        self.assertEqual(d.a, 1)                # 断言 d.a 等于 1
        self.assertEqual(d.b, 'test')
        self.assertTrue(isinstance(d, dict))    # 断言 d 确实是 dict 的实例

    def test_key(self):                         # 测字典取值
        d = Dict()
        d['key'] = 'value'
        self.assertEqual(d.key, 'value')        # 键赋值后，点属性能读到

    def test_attr(self):                        # 测属性赋值
        d = Dict()
        d.key = 'value'
        self.assertTrue('key' in d)             # 属性赋值后，键确实进去了
        self.assertEqual(d['key'], 'value')

    def test_keyerror(self):                    # 测不存在的键抛 KeyError
        d = Dict()
        with self.assertRaises(KeyError):
            value = d['empty']

    def test_attrerror(self):                   # 测不存在的属性抛 AttributeError
        d = Dict()
        with self.assertRaises(AttributeError):
            value = d.empty
```

代码里的注释就是骨架：**一个测试方法只测一件事**，名字起得让人一眼知道在测什么。

## 两种最核心的断言

原文重点提了两个，够你应付绝大多数场景。

**第一种：`assertEqual(a, b)`**，判断两个值是否相等。这是用得最多的：

```python
self.assertEqual(abs(-1), 1)        # 断言 abs(-1) 的结果等于 1
```

**第二种：`assertRaises(ErrorType)`**，判断某段代码会不会抛出指定异常。**一定要配合 `with` 用**：

```python
with self.assertRaises(KeyError):
    value = d['empty']              # 这行应该抛 KeyError，测试才算通过
```

用 `with` 是因为 `assertRaises` 需要**把它内部的代码块整个接管**，代码块抛了指定异常，测试通过；没抛，测试失败。不用 `with` 就起不到“监控这段代码”的效果。

## 怎么把测试跑起来

两种方式，任选：

**方式一：脚本入口**，在 `mydict_test.py` 末尾加两行：

```python
if __name__ == '__main__':
    unittest.main()
```

然后像普通脚本一样跑：`python mydict_test.py`。

**方式二：命令行直接指定模块**，不用改文件：

```bash
python -m unittest mydict_test
```

两种都行，习惯哪个用哪个。

## `setUp` 和 `tearDown`：每个测试方法前后的固定动作

这是原文提到的进阶点，但非常有价值。如果每个测试方法里都要重复“建数据库连接”或者“打开文件”，就把它们抽到 `setUp` 里；对应的清理动作放进 `tearDown`。

```python
class TestDict(unittest.TestCase):

    def setUp(self):                    # 每个测试方法执行前都会跑一次
        print('setUp...')

    def tearDown(self):                 # 每个测试方法执行后都会跑一次
        print('tearDown...')
```

注意：**是每个测试方法前后各跑一次**，不是整个测试类只跑一次。每个 `test_xxx` 都是独立的，互不影响。

## 几个容易踩的坑

**1. 方法名不以 `test_` 开头，根本不会被跑。** 你以为写了测试，其实 `unittest` 压根没理它。写完看到测试数量不对，先检查方法名。

**2. `assertRaises` 忘了写 `with`。** 不写 `with`，它不会监控任何代码，测试永远通过，你测了个寂寞。

**3. 测试代码本身也会有 bug。** 原文专门提过这一点：单元测试不通过，不一定是业务代码错了，也可能是**测试写错了**。所以测试失败时，先看是代码问题还是测试问题。

**4. 测试用例要覆盖边界和异常。** 光测“正常输入”不够，`0`、空值、非法类型、不存在的键，这些才是 bug 的高发区。
