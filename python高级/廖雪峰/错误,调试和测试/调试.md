
## 先搞清楚：调试要解决什么

程序一次写对跑通的概率极低，bug 必然存在。有的 bug 看一眼报错就懂，有的则很隐蔽——**你需要知道出错那一刻，哪些变量的值是对的、哪些是错的**。调试手段就是帮你“偷看程序内部状态”的工具。

廖雪峰列了五种：`print` → `assert` → `logging` → `pdb` → IDE。**不是越往后越高级就越要用，而是按场景选**。下面逐个说。

---

## 一、`print()`：简单粗暴，但有“后遗症”

最直觉的办法，把可疑变量的值打出来：

```python
def foo(s):
    n = int(s)
    print('>>> n = %d' % n)   # 偷看 n 是多少
    return 10 / n
```

跑一下，输出里能看到 `n = 0`，然后才报 `ZeroDivisionError`，问题一下就定位了。

**最大的毛病**：调试完**得手动删**。如果到处塞 `print`，运行结果里全是垃圾信息，而且容易漏删。

**适用场景**：快速验证一个简单假设，临时用一下，用完就删。

---

## 二、`assert`：把 `print` 换成“自动检查”

`assert` 的思路是：**把“我预期这里应该是什么”写成断言**，不满足就直接抛 `AssertionError`，并带上你写的消息。

```python
def foo(s):
    n = int(s)
    assert n != 0, 'n is zero!'   # 断言 n 不为 0，否则抛异常并显示这句话
    return 10 / n
```

跑 `foo('0')`，会抛出 `AssertionError: n is zero!`，**错误信息和出错位置直接告诉你“这里预期错了”**。

**关键开关**：启动解释器时加 `-O`（大写字母 O，不是数字 0），所有 `assert` 会被**当成 `pass` 忽略掉**。这意味着：

- **开发阶段**：开着 `assert`，帮你抓错误；
- **生产环境**：用 `-O` 关掉，不影响性能。

**但坑也在这**：`assert` 不是用来做“用户输入校验”的，它会被 `-O` 干掉。**校验业务数据用 `if + raise`，`assert` 只用于“我作为开发者认为不可能发生”的断言**。

---

## 三、`logging`：不会删的 `print`

`print` 要删，`assert` 会被关，`logging` 解决的就是**“我想留着一堆调试信息，但不想污染输出、不想手动删”**的问题。

```python
import logging
logging.basicConfig(level=logging.INFO)   # 配置日志级别，不配的话 info 不会显示
s = '0'
n = int(s)
logging.info('n = %d' % n)                # 用 info 级别打一条
print(10 / n)
```

输出里会有 `INFO:root:n = 0`，然后才是除零错误。

**核心机制是“级别”**：`debug` < `info` < `warning` < `error`。你在 `basicConfig` 里设了 `level=INFO`，那么 `logging.debug` 就不会输出；设成 `WARNING`，`debug` 和 `info` 都不输出。

**好处**：

- **不用删**：调试信息保留在代码里，通过调整级别控制“现在想看多少”；
- **可以同时输出到多个地方**：控制台 + 文件，一条配置搞定。

**日常建议**：用 `logging` 替代到处塞 `print` 的习惯，尤其是有一定规模的代码。

---

## 四、`pdb`：真正的“单步调试器”

前面三种都是“打信息出来看”，`pdb` 是**让程序停下来，你一步一步走，随时查看现场**。

启动方式：命令行加 `-m pdb`：

```bash
python -m pdb err.py
```

启动后，pdb **停在第一行等待你**，不会自动跑。

**最常用的几个命令**：

| 命令 | 全称 | 作用 |
|---|---|---|
| `l` | list | 查看当前行附近的代码 |
| `n` | next | 执行下一行（**不进入**函数内部） |
| `s` | step | 执行下一行（**进入**函数内部） |
| `p 变量名` | print | 查看某个变量的当前值 |
| `c` | continue | 继续运行，直到下一个断点或结束 |
| `q` | quit | 退出调试 |

此外，也可以在代码里**手动埋断点**：

```python
import pdb
pdb.set_trace()   # 程序跑到这里会自动停下来，进入 pdb 交互
```

或者用 Python 3.7+ 的内置 `breakpoint()`，效果一样，更简洁。

**`pdb` 适合什么**：`print` 和 `logging` 解决不了的“动态问题”——你需要**停下来、反复检查多个变量、甚至改变执行路径**的时候。

---

## 五、IDE 图形调试：最舒服的日常选择

廖雪峰原文也提到 IDE（如 PyCharm、VS Code）的图形化调试器。它的底层能力跟 `pdb` 是一回事——**断点、单步、查看变量、调用栈**——但交互是图形化的，不用记命令，点击就行。

**日常写业务代码，IDE 调试是最优先的选择**。`pdb` 留给“服务器上没有图形界面、只能命令行”的场景。

---

## 怎么选：一张决策表

| 场景 | 用什么 |
|---|---|
| 临时看一眼某个变量 | `print`，用完删 |
| 想留一条“不该发生”的检查 | `assert`，配 `-O` 控制开关 |
| 需要长期保留的调试信息 | `logging`，按级别控制输出 |
| 需要程序停下来、单步排查 | IDE 调试器（优先）或 `pdb` |
| 服务器环境无图形界面 | `pdb` |

---

## 几个容易踩的点

**1. `assert` 会被 `-O` 干掉**，所以**不要用它做用户输入校验**，校验用 `if not valid: raise ValueError(...)`。

**2. `logging` 不配 `basicConfig` 时，`info` 和 `debug` 默认不输出**，不是代码写错了，是级别没设对。

**3. `pdb` 的 `n` 和 `s` 别搞混**：`n` 不进入函数，`s` 进入函数。排查“问题在函数内部”时用 `s`。

**4. `print` 调试完一定要删**，否则生产代码里全是垃圾输出，而且可能泄露敏感信息。
