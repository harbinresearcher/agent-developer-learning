# 错误处理 · 笔记

## 为什么不用错误码

低级写法是让函数返回 `-1` 表示出错，但正常结果和错误码混在一起，调用方**每一层都得写 `if` 判断**，错误还要一级一级往上上报。

Python 的方案是 `try...except...finally`：**正常代码和错误处理代码分开**，错误自动向上层传递，上层不处理就继续往上抛，直到被捕获或程序退出。

---

## 核心语法：try、except、else、finally

```python
try:
    print('try...')
    r = 10 / 0                     # 出错，后续 print 不执行
    print('result:', r)
except ZeroDivisionError as e:     # 捕获除零错误
    print('except:', e)
else:
    print('no error!')             # 没有错误才执行
finally:
    print('finally...')            # 无论如何都执行
print('END')                       # 整个结构之后，程序继续往下走
```

**执行流程**：`try` 里一旦出错，**当前 `try` 剩余代码直接跳过**，跳到匹配的 `except`；`except` 执行完，如果有 `finally` 就走 `finally`，然后继续 `END`。没出错的话，`except` 跳过、`else` 执行、`finally` 照样执行。

`else` 和 `finally` 都是可选的。`finally` 最典型的用途是**资源清理**，比如关文件、关连接，不管前面有没有炸，都得关。

---

## 错误也是 class，`except` 会连子类一起抓

Python 里所有错误都继承自 `BaseException`，常见的业务错误大多继承自 `Exception`。这带来一个关键行为：**`except` 在匹配时，不只看类型是否完全相等，子类也会被父类的 `except` 抓走**。

```python
try:
    foo()
except ValueError as e:            # 先抓 ValueError
    print('ValueError')
except UnicodeError as e:          # UnicodeError 是 ValueError 的子类
    print('UnicodeError')          # 永远走不到这里
```

`UnicodeError` 是 `ValueError` 的子类，当它抛出时，第一个 `except ValueError` 已经把它截胡了，第二个 `except` 是死代码。所以**写多个 `except` 时，子类必须放在父类前面**，否则子类分支永远不生效。

---

## 跨越多层调用：在合适的层次捕获就行

`try...except` 的一个巨大好处是**不需要每个函数都写**。`main()` 调 `bar()`，`bar()` 调 `foo()`，`foo()` 炸了，只要 `main()` 里捕获，错误会自动穿过 `bar` 和 `foo` 传到 `main`。

```python
def foo(s):
    return 10 / int(s)             # 可能炸

def bar(s):
    return foo(s) * 2              # 不处理，让它往上抛

def main():
    try:
        bar('0')                   # 在顶层捕获
    except Exception as e:
        print('Error:', e)
    finally:
        print('finally...')
```

这叫**在合适的层次捕获**。底层函数只管干活，错误处理交给知道“出错之后该干什么”的上层。

---

## 调用栈：错误没被抓住时会怎样

如果错误一直没人捕获，它会**一路往上抛，最后被 Python 解释器接住，打印调用栈，然后程序退出**。调用栈（Traceback）从下往上读，最底下那行是**真正出错的位置和原因**，中间是调用链，最上面是程序入口。

看到 `Traceback` 别慌，**先读最下面那一行**，它是错误类型和消息；然后顺着调用链往上找，看是谁调用了出事的函数。

---

## 记录错误：`logging.exception`

如果不想让程序退出，但又要保留完整错误信息，就在 `except` 里用 `logging.exception(e)`：

```python
import logging

try:
    bar('0')
except Exception as e:
    logging.exception(e)           # 打完整调用栈，程序继续往下走
```

`logging.exception` 的特别之处是：**它自动把当前异常的完整 Traceback 一起打出来**，等价于 `logging.error(..., exc_info=True)`。不用你自己去拼错误信息，调用栈原样保留，方便事后排查。

---

## 抛出错误：`raise`

`raise` 是你**主动制造一个错误**。

**抛内置错误**：

```python
def foo(s):
    n = int(s)
    if n == 0:
        raise ValueError('invalid value: %s' % s)   # 主动抛，带上说明
    return 10 / n
```

**抛自定义错误**：先定义一个继承 `Exception` 的类，再 `raise` 它的实例。但廖雪峰的建议是：**能用内置错误类型（`ValueError`、`TypeError` 等）就别自己造**，自定义异常只在确实需要区分业务语义时才用。

**重抛（非常常用）**：在 `except` 里处理完日志或清理后，用**不带参数的 `raise`** 把原异常继续往上抛，让上层决定怎么处理。

```python
def bar():
    try:
        foo('0')
    except ValueError as e:
        print('ValueError!')
        raise                      # 重抛同一个异常，上层还能接住
```

注意：**光 `logging.exception` 不 `raise`，错误就被“吞掉”了**，上层不知道出过事；**光 `raise` 不 `logging`，调用栈会在上层重新生成，但可能丢失一些上下文**。两者按需搭配。

---

## 几个容易踩的点

**1. `except` 顺序：子类在前，父类在后。** 反过来写，子类分支是死代码，永远不执行。

**2. `finally` 一定会执行，即使 `except` 里又抛了错误。** 所以清理逻辑放 `finally` 最稳。

**3. 不要空 `except: pass`。** 裸 `except` 会连 `KeyboardInterrupt`、`SystemExit` 这种“不是错误而是信号”的东西一起吞掉，程序可能停都停不下来。**至少写 `except Exception`，并且别 `pass`**，要么记日志，要么 `raise`。

**4. `raise` 不带参数只能在 `except` 块里用**，它重抛的是“当前正在处理的异常”，出了这个块就没有“当前异常”了。
