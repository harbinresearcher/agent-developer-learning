# UDP编程 · 笔记

## 先钉死定性：UDP和TCP的根本区别

原文第一段就把核心差异说透了：**TCP是建立可靠连接、以流的形式发送数据**，**UDP是面向无连接的协议**，不需要建立连接，只需要知道对方的 IP 和端口，就可以直接发数据包。

“**能不能到达就不知道了**”，这句不是吓唬人，是UDP的本质属性。它不保证顺序、不保证不丢包、也不保证不重复。换来的东西是**速度快**，所以在视频直播、在线游戏这类“丢一两帧无所谓，但卡一下很难受”的场景里，UDP 反而是更合理的选择。

写代码时，这个差异会直接体现在 **Socket 的类型**上：TCP 是 `SOCK_STREAM`，UDP 是 `SOCK_DGRAM`。`DGRAM` 就是 datagram（数据报）的缩写，**一个包就是一个完整的数据报**，不会像 TCP 那样被拆成字节流。

## 服务器端：绑定端口，直接等数据

UDP 服务器比 TCP 服务器简单得多，因为**它不需要 `listen()`，也不需要 `accept()`**。

```python
import socket

s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)   # 创建 UDP Socket，SOCK_DGRAM 是 UDP 的类型标识
s.bind(('127.0.0.1', 9999))                            # 绑定本机 127.0.0.1 的 9999 端口
print('Bind UDP on 9999...')

while True:                                            # 服务器要持续运行
    data, addr = s.recvfrom(1024)                      # 阻塞等待，直到收到一个数据报，返回 (数据, 客户端地址)
    print('Received from %s:%s.' % addr)               # 打印是谁发来的
    s.sendto(b'Hello, %s!' % data, addr)               # 直接把“Hello + 原数据”发回给这个地址
```

**`recvfrom()` 是 UDP 服务器最核心的方法**。它一次返回两个东西：**收到的数据**，以及**发送方的地址和端口**。你拿到这个 `addr`，紧接着用 `sendto()` 往这个地址回数据，就是一个完整的“收→回”闭环。

`sendto()` 的参数是 `(要发送的 bytes, 目标地址元组)`。**目标地址必须是 `(IP, port)` 的元组**，不能只写 IP。

**注意原文这里没有开多线程**，不是忘了，是因为例子足够简单。UDP 服务器天然可以串行处理，因为 `recvfrom()` 每次只拿一个包，处理完再拿下一个，不会像 TCP 那样出现“一个客户端占着连接不放”的问题。

## 客户端：不连，直接发

TCP 客户端要先 `connect()`，UDP 客户端**跳过这一步**，直接 `sendto()` 把数据往服务器地址一扔就行。

```python
import socket

s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)   # 同样创建 UDP Socket
for data in [b'Michael', b'Tracy', b'Sarah']:           # 发送三个名字
    s.sendto(data, ('127.0.0.1', 9999))                 # 直接发往服务器的 IP 和端口
    print(s.recv(1024).decode('utf-8'))                 # 接收服务器返回的响应，用 recv 就行
s.close()
```

**接收响应时用的是 `recv()`，不是 `recvfrom()`**。因为客户端在 `sendto()` 之后，相当于默认“我在等这个服务器的回复”，`recv()` 直接拿到数据本身，不需要再关心是谁发来的。

## 坑一：UDP 和 TCP 的端口可以“同名”

原文小结里专门强调了这一点：**UDP 的 9999 端口和 TCP 的 9999 端口可以各自绑定，互不冲突**。

这意味着，你完全可以在同一台机器上，**同时跑一个 TCP 服务和一个 UDP 服务，都用 9999 端口**，操作系统不会报错。因为 TCP 和 UDP 在协议栈里是两套独立的端口空间。不要因为看到“9999 已经被用了”就以为 UDP 不能用，它们不共享端口。

## 坑二：`recvfrom()` 的缓冲区大小不是“上限”

`s.recvfrom(1024)` 里的 `1024` 是**这一次最多接收多少字节**。如果发送方发来的数据报超过 1024 字节，**多出来的部分会被直接丢弃**，而且**没有任何警告**。

UDP 数据报的理论最大长度是 **65507 字节**（IPv4 下，65535 减去 8 字节 UDP 头再减去 20 字节 IP 头）。但实际传输时，**超过路径 MTU（通常是 1500 字节左右）的数据报会被 IP 层分片**，分片会显著增加丢包后的整体损失——只要丢一个分片，整个数据报就废了。所以实际写代码时，**UDP 数据报最好控制在 MTU 以内**，不要真的去试探 65507 的上限。

## 坑三：`recvfrom()` 是阻塞的，没有数据就干等

`recvfrom()` 默认是**阻塞调用**：如果没有数据到达，程序就停在那一行，什么也不干。

这在服务器的主循环里是正常的，但在某些场景下会出问题——比如你想“等一小会儿，没数据就去做别的事”，直接 `recvfrom()` 会把你卡死。需要非阻塞行为时，得用 `s.setblocking(False)` 配合异常处理，或者用 `select`/`selectors` 来监控多个 Socket。原文这页没有展开，但知道这个默认行为的存在，以后遇到“程序卡住不动”时，第一反应就能想到它。

## 这页记住三件事

1. **UDP 不建连接、不可靠、但快**，Socket 类型是 `SOCK_DGRAM`，不是 `SOCK_STREAM`。
2. **服务器 `bind` 之后直接 `recvfrom`，客户端不 `connect` 直接 `sendto`**；`recvfrom` 一次拿到数据和对方地址，`sendto` 把响应发回那个地址。
3. **UDP 端口和 TCP 端口互不冲突**；`recvfrom` 的缓冲区大小是“截断线”，超过就丢，且没有警告。
