# 异步IO · 笔记

## 先聊痛点：CPU 太快，I/O 太慢

原文开篇点得很准：**CPU 的速度远远快于磁盘、网络等 I/O**。在一个线程里，你发一个网络请求，**线程就被挂起，什么都干不了，只能干等 I/O 返回**。这就是**同步 IO**。

怎么办？传统方案是多线程或多进程，每个用户一个线程，一个线程在等 I/O 的时候，操作系统切到另一个线程去跑。但原文也说了它的代价：**系统不能无上限地增加线程**，线程切换本身要花时间，线程一多，CPU 大量时间浪费在切换上，真正干活的时间反而少了。

异步 IO 换了一个思路：**遇到耗时 I/O 时，只发出 I/O 请求，不等待结果，转身去执行其他代码；一段时间后 I/O 完成了，再来处理结果**。

---

## 核心机制：事件循环（Event Loop）

同步代码没法直接实现异步，因为 `f.read()` 这一行天然就会把线程停住。所以异步 IO 需要一个**消息循环**，主线程不停地重复“读取消息 → 处理消息”这个过程。

你可以把**事件循环**想象成一个**单线程的调度员**。它手里有一堆任务（协程），挨个执行：

- 执行到某个任务的 `await`，发现“这里要等 I/O”，**调度员把这个任务先放一边**，转身去执行下一个任务；
- 某个任务的 I/O 完成了，调度员再回来**从暂停的地方接着执行**。

原文用 GUI 程序打了个比方：GUI 主线程不停地处理键盘、鼠标消息，**如果某个消息处理时间过长，整个界面就卡死无响应**。异步事件循环同理：**一旦你在里面写了一个阻塞操作，整个循环就被卡住了**，所有任务都得排队。

**一句话钉死**：**事件循环是单线程的，它高效的前提是“永远不阻塞”**。

---

## asyncio 三件套：`async def`、`await`、`Task`

Python 的异步能力来自 `asyncio`，你实际动手写的就三个东西。

### `async def`：定义协程函数

```python
async def fetch_data():          # async def 定义的是一个协程函数
    await asyncio.sleep(1)       # await 表示“这里要等，等的期间让出控制权”
    return {"data": 123}
```

**关键认知**：调用 `fetch_data()` **不会立刻执行函数体**，它只是返回一个**协程对象**，相当于一张“待办纸条”。真正驱动它执行的是 `await` 或事件循环。

### `await`：把控制权交还给事件循环

`await` 只能写在 `async def` 里面。执行到 `await` 时，**当前协程暂停，事件循环可以去跑别的任务**；等 `await` 后面的操作完成了，再从暂停处恢复。

**这是异步的核心动作**：不是“等”，而是“**在等的时候把执行权让出去**”。

### `asyncio.gather` / `create_task`：并发执行多个协程

如果你有多个协程要跑，直接顺序 `await` 是串行的。要并发，得用 `asyncio.gather`：

```python
async def main():
    results = await asyncio.gather(     # 三个协程并发执行，总共只花约1秒，不是3秒
        fetch_data(),
        fetch_data(),
        fetch_data()
    )
```

`asyncio.gather` 把多个协程**同时扔进事件循环**，谁先准备好就处理谁，最后按传入顺序返回结果列表。`asyncio.create_task` 则是“把一个协程包装成任务，立刻丢进事件循环开始跑”，适合“不等待、先跑着”的场景。

## FastAPI 里最重要的一条规矩：`async def` 还是 `def`

FastAPI 官方文档把这件事说得非常清楚，直接照搬结论：

**你的函数里用了支持 `await` 的库 → 写 `async def`。** 比如数据库驱动、HTTP 客户端告诉你“用 `await` 调我”，那就 `async def` + `await`。

**你的库不支持 `await` → 老老实实写普通 `def`。** FastAPI 会自动把普通 `def` 丢进**线程池**里跑，**不会阻塞事件循环**。

**拿不准？写 `def`。**

**为什么这条规矩这么重要**：如果你在 `async def` 里调用了**同步阻塞**的库（比如 `requests`、`time.sleep`、同步版数据库驱动），**事件循环就被你卡死了**，所有请求都得排队，异步的并发优势直接归零。

```python
@app.get("/bad")
async def bad():
    time.sleep(3)          # 阻塞！事件循环卡死3秒，其他请求全排队
    return {"msg": "done"}

@app.get("/good")
def good():
    time.sleep(3)          # 普通 def，FastAPI 丢线程池，不卡事件循环
    return {"msg": "done"}
```

## 调外部接口：用异步客户端，别用 `requests`

在 FastAPI 里如果需要调用第三方 HTTP API，**绝对不能在 `async def` 里用 `requests`**，因为 `requests` 是同步阻塞的。要用异步 HTTP 客户端，比如 `aiohttp`（或者 `httpx` 的异步模式）。

`aiohttp` 的标准用法：

```python
import aiohttp

async def fetch(url):
    async with aiohttp.ClientSession() as session:   # 创建异步会话
        async with session.get(url) as response:       # 发起异步 GET 请求
            return await response.json()               # 异步读取 JSON
```

**`aiohttp.ClientSession` 应该在应用启动时创建一次、全局复用**，而不是每个请求都新建一个。FastAPI 的 `lifespan` 机制就是干这个的：启动时把 session 挂在 `app.state` 上，关闭时统一 `close()`。

**性能差距有多大**：同步 `requests` 串行发 100 个耗时 0.5 秒的请求，要 50 秒左右；`aiohttp` + `asyncio.gather` 并发发 100 个，**总耗时约 0.5 秒**，因为 100 个请求的等待时间被完全重叠了。

## 几个必须盯死的坑

**① 在 `async def` 里写阻塞代码，等于自废武功。** 事件循环是单线程的，一个阻塞操作卡住，所有并发请求全部停摆。

**② `await` 只能写在 `async def` 里。** 普通 `def` 里写 `await` 直接语法错误。

**③ 协程对象不 `await` 不会执行。** `fetch_data()` 返回的是协程对象，你 `await fetch_data()` 或者把它丢进 `gather` 才会真正跑起来。

**④ `aiohttp.ClientSession` 不要每次请求都新建。** 它内部维护连接池，反复创建销毁会浪费资源。用 `lifespan` 在应用级别创建一次。

**⑤ 拿不准同步还是异步时，写 `def` 是安全的。** FastAPI 会把普通 `def` 丢线程池，不会卡事件循环；写错了 `async def` 反而可能把整个应用卡死。

---

## 一句话收束

**异步 IO 的核心是事件循环：遇到 I/O 不傻等，把控制权让出去跑别的，I/O 好了再回来。在 FastAPI 里，库支持 `await` 就写 `async def`，不支持就写 `def`，拿不准写 `def`；调外部接口用 `aiohttp`，`ClientSession` 在应用级别复用。**
