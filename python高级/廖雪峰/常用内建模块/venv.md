## 📦 虚拟环境是干什么的

虚拟环境就是为了解决不同项目需要同一个库的不同版本时互相冲突的问题。

`venv` 是 Python 3.3 开始自带的**轻量级**虚拟环境模块，不需要额外安装任何东西。核心作用就是**创建相互独立的“沙箱”**，每个环境有自己的解释器入口和 `site-packages` 目录；解释器可以是复制或符号链接，在不同沙箱里装包互不干扰。

## 🛠️ 标准用法四步走

在项目根目录下依次执行：

**第一步：创建虚拟环境**

```bash
python -m venv .venv
```

这会在当前目录下生成一个名为 `.venv` 的文件夹（用 `.` 开头是惯例，方便在系统中隐藏）。其中包含环境的解释器入口，通常也会安装 `pip`。

**第二步：激活虚拟环境**

- **Windows PowerShell**：`.\.venv\Scripts\Activate.ps1`；命令提示符使用 `.venv\Scripts\activate.bat`。
- **macOS / Linux**：`source .venv/bin/activate`

激活后，**终端提示符前面会出现 `(.venv)`**，表示你当前已经进入了这个虚拟环境。激活的本质是调整环境变量 `PATH`，让命令行优先使用虚拟环境里的 `python` 和 `pip`。

**第三步：安装依赖包**

```bash
pip install requests
```

激活状态下，`pip` 会**自动把包装进当前虚拟环境的 `site-packages`**，而不会影响系统全局的 Python 环境。

**第四步：退出虚拟环境**

```bash
deactivate
```

退出后终端提示符前面的 `(.venv)` 消失，你回到系统全局环境。

## ⚠️ 必须搞懂的三个核心认知

**① `.venv` 绝对不能提交到 Git**
虚拟环境目录**不应被签入版本控制系统**（如 Git）。它是“可丢弃的”——删掉后随时能用 `requirements.txt` 重建。记得在 `.gitignore` 里加上 `.venv/`。

**② venv 是“包级隔离”，不是“Python 版本级隔离”**
`venv` **不负责切换 Python 版本**。你用 Python 3.9 创建的环境，永远只能用 3.9 跑。想用 3.8？得先有一个 3.8 的 Python，再用它重新执行 `python3.8 -m venv .venv`。

**③ conda 与 venv 的选择**
conda 用户通常用 conda 管理环境和非 Python 依赖；是否使用 venv 取决于解释器及项目要求。优先沿用项目约定，避免混淆解释器和安装位置。

## 🚀 知道有这么回事：uv

`venv` 是官方标准、足够稳、不用额外装东西，**新手优先用它**没问题。

但可以了解一个趋势：**`uv`** 是近两年兴起的新工具（Rust 编写），用一条命令同时接管了“建环境 + 装包 + 锁版本”，可加速依赖解析和安装，实际速度取决于工作负载，并且能自动管理 Python 解释器版本。你现阶段用 `venv` 入门完全够用，等以后项目多了、觉得 `pip install` 太慢，再去了解 `uv` 也不迟。
