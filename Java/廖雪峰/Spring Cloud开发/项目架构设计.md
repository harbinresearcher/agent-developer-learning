# 项目架构设计

> **重要程度：高**｜**手练：需要**
> **重点**：交易对与报价；从下单到撮合、清算、行情和推送的链路；每个服务的数据责任和故障边界。

## 先认识交易对

教程以 BTC/USD 为例：BTC 是**基础资产**，USD 是**计价资产**。价格 100 USD/BTC 表示 1 BTC 的报价为 100 USD。买入 0.5 BTC、单价 100 USD/BTC，成交金额是 `0.5 × 100 = 50 USD`。这是简化示例；真实市场还要考虑手续费、价格精度、数量精度和舍入规则。

限价买单给出愿意支付的最高价，限价卖单给出愿意接受的最低价。当买价不低于卖价时，订单可能成交；具体成交价格、撮合规则以交易系统规则为准。教程为了聚焦主线，只考虑一个交易对，不处理手续费、充值提现、完整风控和运营后台。

## 订单从哪里来，到哪里去

```text
用户 → UI → API → 定序 → 交易引擎
                          ├→ 成交结果 → 行情聚合 → K线
                          └→ 订单与资产变化 → 推送 → 用户
```

1. **UI** 收集用户操作、展示订单和行情；前端校验提高体验，但服务端仍要独立校验。
2. **API** 做身份认证、参数校验并提交下单或撤单请求；查询接口返回可查询的订单或资产状态。请求超时不代表订单一定未创建。
3. **定序系统** 给被接受的事件确定顺序，向引擎提供可重放的输入；多个服务各自记录时间戳并不能自然形成可靠全局顺序。
4. **交易引擎** 跟踪订单、冻结资产、撮合买卖并清算。撮合负责计算成交，清算负责按成交结果更新双方资产。
5. **行情系统** 根据成交记录聚合价格与数量，例如按一分钟生成 K 线；行情是对成交事件的派生视图。
6. **推送系统** 向客户端发送行情与订单变化。连接断开或消息丢失后，客户端要能重连并用权威查询接口补齐，不能只靠推送消息。

教程采用 MySQL、Kafka、Redis 等组件分别承担持久化、事件传递和缓存等职责。组件名称不自动赋予一致性：必须明确什么数据最权威、何时写入、失败后如何恢复。

## 用一笔订单走完整条链

假设买家有 100 USD，提交限价单买 0.5 BTC，价格 100 USD/BTC。为简化计算，假设订单立即以同价全部成交，且没有手续费：

1. API 校验身份、数量和价格，给这次业务请求设置稳定的请求 ID。
2. 事件进入定序流，获得位置；引擎按顺序处理。
3. 引擎检查买家 USD 可用余额，冻结 50 USD；卖家对应的 BTC 也需要已冻结或按规则冻结。
4. 撮合生成一笔数量 0.5 BTC、成交金额 50 USD 的成交记录；清算后买家获得 0.5 BTC，卖家获得 50 USD。
5. 行情按成交时间窗口更新 K 线，推送告知各自用户；用户重连时通过订单和资产查询确认最终状态。

这只是理想路径。余额不足时不得生成有效成交；部分成交需要区分已成交量、剩余量和剩余冻结金额；价格改善、撤单、重复请求和服务崩溃都需要专门规则。

## 找工作时要讲出的工程边界

- **数据一致性**：订单、余额、事件和推送不一定在同一事务；明确原子提交边界、幂等键、outbox、补偿及对账。
- **可靠恢复**：保存事件日志、消费进度和快照，重放时验证版本、顺序和状态；快照不是备份恢复演练的替代品。
- **安全和风控**：真实系统还需要授权、审计、限流、防重放、价格与数量边界、异常交易识别、密钥管理及适用监管要求。教学架构不等于可上线的交易所。
- **容量和可观测性**：监控 API 错误率和延迟、事件积压、撮合延迟、资产不平衡与推送连接；按业务后果设计告警。

## 自测与手练

1. 改成只成交 0.2 BTC，订单剩余多少 BTC？在不考虑手续费与价格改善的前提下，剩余冻结多少 USD？（答案：0.3 BTC、30 USD。）
2. 客户端请求超时后立即用新 ID 重试，可能出现什么问题？应如何查询或使用原请求 ID？
3. 为什么 K 线和 WebSocket 消息通常不能代替权威的订单及资产记录？
4. 任选一次服务重启，画出它从哪里读取持久化状态、从什么位置重放以及如何验证恢复结果。
