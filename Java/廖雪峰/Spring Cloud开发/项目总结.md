# Spring Cloud 项目总结

> **重要程度：高**｜**手练：需要**
> **重点**：梳理请求链路和数据归属；用超时、幂等、补偿处理失败；理解日志、指标和链路追踪的分工。

## 先把项目说清楚

教程以交易系统为例，把用户入口、交易引擎、定序、行情和推送等职责拆开。拆分带来的好处是职责可以独立演进；代价是原来同一进程中的调用变成网络调用，会遇到超时、重复、顺序错乱和部分成功。

```text
用户 → UI / 网关 → API → 定序 → 交易引擎 → 结果持久化
                                    ├→ 行情
                                    └→ 推送 → 用户
```

这是学习用的职责示意，不代表这些箭头都有原子性或可靠投递保障。阅读各章节时，要给每一步标明输入、输出、数据由谁保存、失败后由谁重试。

## 一个下单请求的失败分析

假设用户提交订单 `clientOrderId=A123`，服务接受请求后网络断开，用户没有收到响应。此时无法只凭超时判断订单是否创建：请求可能没有到达，也可能订单已创建但响应丢失。

1. 客户端用同一个业务请求 ID 查询或重试；不能每次重试都生成新 ID。
2. 服务端把用户和请求 ID 与请求结果绑定，使用持久化唯一约束保证重复请求不会重复创建订单；不同请求内容复用同一个 ID 应拒绝。
3. 订单状态变化和后续事件通知之间需要一致性方案，例如同一数据库事务写入订单及 outbox，再由后台发送事件。消费者仍需要去重。
4. 如果事件处理失败，记录失败和重试次数；达到上限进入待处理队列，并让运营或值班人员有查询、补偿入口。
5. 用同一追踪标识关联入口、下游调用和日志，但追踪 ID 不是业务幂等键，也不能代替数据库约束。

这些是工程设计方向；是否严格保序、如何避免双花和如何恢复状态，都必须按实际业务设计和测试。交易系统涉及资金与安全，教程示例不能直接当作生产交易系统。

## 服务拆分后需要补什么

- **入口与安全**：网关集中做 TLS、路由和限流；身份认证、资源授权仍需明确责任。内部调用也要有身份与权限校验，不能因为来自内网就默认可信。
- **远程调用**：设置连接和读取超时；只对适合重试的故障做有限重试，加退避和抖动。非幂等操作重试前必须有幂等机制。熔断和降级需要结合业务，不能把失败伪装为成功。
- **状态与顺序**：明确订单、余额和撮合状态的权威数据源；消息可能重复或乱序，消费者要校验版本、顺序或通过分区设计控制顺序，并处理异常。
- **发布与恢复**：配置外置、密钥专门管理；检查版本兼容、数据库迁移、灰度和回滚，定期备份并演练恢复。
- **负载与资源**：限制线程池、连接池和队列容量；观察排队与积压，过载时及时拒绝或降级，避免请求层层堆积。

## 可观测性：先定位，再追原因

- **日志**回答发生了什么：记录订单 ID、操作、结果和错误原因；脱敏，禁止输出密码、令牌和完整敏感信息。
- **指标**回答规模和趋势：请求量、错误率、延迟分位数、队列积压、撮合或清算失败数；用阈值与持续时间配置告警，避免高基数标签把监控系统拖垮。
- **链路追踪**回答一次请求经过哪些服务、耗时在哪里：用 trace 和 span 关联跨服务调用。采样意味着并非每个请求都一定可查到完整链路。

教程提到 Spring Cloud Sleuth；新项目应按当前 Spring Boot 的 Micrometer Observation / Tracing 文档选型，而不是照搬旧依赖。教程列出的 StatsD 只是指标传输方案之一，不应假定它适合所有系统。Spring Cloud 与 Spring Boot 的版本兼容关系要以官方发布列车说明为准。

## 手练：做一次故障走查

1. 在 [[Java/廖雪峰/Spring Boot开发/使用Actuator|Actuator]] 笔记中启动已验证的示例，访问健康端点，确认返回状态。
2. 对上面的 A123 场景画一条时间线：服务写入成功、响应丢失、客户端重试、服务返回已有结果。分别标出数据库状态和用户看到的状态。
3. 设计三条测试：重复提交同一 ID；同一 ID 携带不同内容；服务提交成功后响应丢失并重试。写出每条的预期订单数量和返回结果。
4. 选择一项故障，比如下游超时，列出需要看的指标、日志字段、追踪信息以及补偿入口。这里只做方案推演，不能视为已完成分布式故障演练。

## 面试自测

1. 网关限流通过了，为什么后端仍要限制线程池和连接池？
2. 客户端调用超时，为什么不能直接判定下单失败？
3. 追踪 ID、请求幂等键和数据库主键分别解决什么问题？
4. 如何证明恢复流程可用，而不是只证明系统做过备份？
