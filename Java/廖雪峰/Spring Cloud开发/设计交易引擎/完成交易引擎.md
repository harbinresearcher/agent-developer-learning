# 完成交易引擎

> **重要程度：高**｜**手练：需要**
> **重点**：按序处理事件的完整链路；状态与副作用分离；快照、重放、缺口检测及状态校验。

## 把组件串成一条处理链

教程的引擎组合资产、订单、撮合和清算四部分，消费经定序的下单、撤单或转账事件。以下是下单的逻辑顺序，具体事务边界需要单独设计：

```text
接收事件 → 去重与缺口检查 → 校验并冻结资产 → 创建订单
         → 撮合 → 清算并更新订单 → 保存处理进度和输出
```

下单创建失败（例如余额不足）时，不应继续撮合。撤单需要先确认订单仍可撤，再撤销剩余数量并释放相应冻结额。转账、下单与撤单都应遵循同一顺序域的规则；每种事件的失败结果也要有明确记录。

## 一条事件从收到到完成

假设持久化游标为 10，收到事件 11（前驱 10），一笔买单需冻结 50 USD：

1. 检查事件号和前驱：11 是新事件，前驱和当前游标一致，可以处理。
2. 校验用户资产和请求；余额足够则冻结 50 并创建订单，余额不足则按业务规则记录拒绝，不生成有效订单。
3. 若有对手单，撮合产生成交记录；清算根据每笔成交更新双方资产及订单。没有对手单则订单保留在订单簿。
4. 将状态更新、处理记录和需要发送的事件可靠保存，再让外部服务获取结果。具体如何原子提交取决于设计；仅更新内存并把任务加入内存队列，进程崩溃时可能丢失。
5. 可恢复地推进游标，记录成功或拒绝结果；之后重放事件 11 时不得再次产生资产变更。

这条链路是分析模型，不表示本笔记提供了完整交易所或已经完成端到端验证。可先手练 [[Java/廖雪峰/Spring Cloud开发/设计定序系统|定序系统]] 中的乱序和去重程序，再运行 [[Java/廖雪峰/Spring Cloud开发/设计交易引擎/设计撮合引擎|撮合引擎]] 的订单簿示例，对照这里标出两者之间还缺少资产和持久化哪些步骤。

## 重复、缺口和恢复

- **重复**：旧序号不能重新应用业务变更；还应区分事件重复与同一业务请求以新序号再次到达。分别维护事件处理记录和业务幂等键。
- **缺口**：当前游标是 10，事件 12 的前驱是 11；先暂停该顺序域，从权威事件日志读取并处理 11，再处理 12。日志不可用或缺失时应告警、阻止继续，不可假定查询必然成功。
- **崩溃重放**：从经过校验的快照恢复状态和快照对应的事件位置，再按序重放后续事件。快照必须对应同一个一致时点，不能资产取自事件 10、订单却取自事件 12。
- **重复副作用**：重放状态不能无条件重新发送成交通知或调用外部转账。用可靠输出记录、稳定事件 ID 和消费者幂等控制副作用；只按时间过滤通知既可能漏发也可能重发。
- **主备切换**：相同输入可能让副本得到相同状态，但必须约束只有合法主节点产生对外副作用，并处理旧主恢复后的栅栏问题。

快照应包含资产、活动订单、订单簿和已处理位置，并有版本、校验值和完整写入机制；恢复后先检查引用关系，再接入实时消费。快照文件损坏、版本不兼容和事件保留不足都需要演练。

## 校验不变量

开发和测试时，在每个事件后检查：

1. 每个用户可用和冻结余额符合业务约束；按资产分别检查完整账本的平衡。内部平衡仍不能替代外部对账。
2. 活动订单的剩余冻结需求与对应资产冻结明细一致；不能只比较全系统总额。
3. 活动订单和订单簿的索引一致；已完成或取消的订单不应仍参与撮合。
4. 订单原始数量与成交、撤销、剩余数量满足约定关系；成交记录和清算流水对应。
5. 引擎记录的事件位置与实际状态一致；同一事件重放后的结果可预期且不会重复外部副作用。

全量校验可能昂贵：生产环境应结合性能要求选择抽样、后台对账和关键路径校验。校验失败要阻止错误扩散并告警，不能只打印日志后继续处理资金。

## 手练与自测

1. 用资产笔记的例子，手算冻结 50、成交需 18、退回价差 2 后的剩余冻结，并与清算笔记核对。
2. 制作故障时间线：状态已更新但游标未提交时崩溃；反过来游标先提交而状态未更新时崩溃。分别说明可能重复或遗漏什么。
3. 快照标记位置 100，却只包含处理到 99 的资产状态，恢复从 101 开始会造成什么问题？
4. 输入、初始状态和代码版本都相同，但引擎根据当前时间决定成交规则，两个副本一定一致吗？
