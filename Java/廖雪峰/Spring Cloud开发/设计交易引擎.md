# 设计交易引擎

> **重要程度：高**｜**手练：需要**
> **重点**：资产、订单、撮合、清算的分工；冻结与解冻；确定性状态机和重放的前提。

## 四个部分各做什么

交易引擎接收按顺序排列的请求，维护订单和资产状态，并输出成交及状态变化。教程将其分成四部分：

- **资产系统**：区分可用与冻结资产；下单时按规则冻结，撤单或未成交部分按规则解冻。
- **订单系统**：记录订单方向、价格、数量、已成交量和状态，控制下单、部分成交、完成、撤单等合法变化。
- **撮合引擎**：维护买卖订单簿，在规则允许时匹配买卖订单，产生成交数量和价格；常见规则是价格优先、同价时间优先。
- **清算系统**：根据成交记录更新双方冻结资产及获得的资产，同时记录流水，确保资产变更可追溯。

先看 [[Java/廖雪峰/Spring Cloud开发/设计交易引擎/设计资产系统|资产系统]]、[[Java/廖雪峰/Spring Cloud开发/设计交易引擎/设计订单系统|订单系统]]，再看撮合和清算；交易规则的具体实现需要在各篇单独学习。

## 一笔部分成交

假设只支持限价单，没有手续费、价格改善或舍入：买家以 100 USD/BTC 买 0.5 BTC，先冻结 50 USD。卖家以同价卖出 0.2 BTC，且已冻结 0.2 BTC。

1. 撮合产生一笔成交：0.2 BTC，金额 20 USD；买单还剩 0.3 BTC，卖单已完成。
2. 清算后，买家获得 0.2 BTC，原冻结 USD 中消耗 20，仍冻结 30；卖家冻结的 0.2 BTC 被消耗，获得 20 USD。
3. 后续若买家撤销剩余订单，剩余冻结的 30 USD 按规则回到可用余额。

上述数值只说明分工。实际系统要规定成交价选择、精度、手续费、资产流水和事务边界；不能只更新订单状态而漏掉余额变化。

## 为什么把引擎看成状态机

状态可以理解为某一时刻的资产、订单和订单簿；事件是下单、撤单、转账等输入；处理一个事件后得到新状态和输出。

```text
旧状态 S0 + 事件 E1 → 新状态 S1 + 输出 R1
新状态 S1 + 事件 E2 → 新状态 S2 + 输出 R2
```

要让两个副本重放后得到相同结果，至少要保证：初始状态相同；输入内容和顺序相同；处理规则和版本相同；使用相同的精度及舍入规则；事件处理不直接依赖未记录的当前时间、随机数、外部接口或不稳定的遍历顺序。时间和随机值如果影响结果，应作为经过校验的事件数据持久化，或采用确定性规则。

只说“事件驱动”不能证明系统确定，也不能自动保证主备切换安全。多个副本若都对外发送通知或执行转账等副作用，需要明确唯一发布者、去重和故障转移机制。

## 内存引擎如何恢复

内存访问快，但断电会失去未持久化状态。常见恢复设计是持久化有序事件，周期性生成带位置的快照：启动时加载经过校验的快照，再从该位置之后重放事件，最后与权威记录或校验值核对。必须测试事件缺失、重复、损坏、快照版本不兼容和主备切换；“有快照”不等于“已经能恢复”。

教程将数据库事务描述为速度慢、TPS 低，这是简化取舍，具体性能要结合数据模型、隔离级别、硬件和实测。数据库事务提供原子性与持久性方面的工具，内存方案则需要另外设计日志、恢复和一致性；两者都要按目标评估。
