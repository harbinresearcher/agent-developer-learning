# 设计定序系统

> **重要程度：高**｜**手练：需要**
> **重点**：事件序号与业务请求 ID 的区别；检查顺序缺口；重复投递去重；持久化、恢复与一致性边界。

## 定序解决什么问题

多个用户可能同时下单、撤单或转账。不同网络连接收到请求的时间不一定能构成所有服务一致认可的先后顺序。定序器为被接受的事件安排明确顺序，交易引擎按该顺序更新状态；不同副本从相同初始状态接收相同事件序列后，才有机会得到相同结果。

教程设计在每个事件上记录 `sequenceId` 和 `previousId`。例如事件 101 的前驱是 100；消费方当前已处理到 98 时却收到了前驱为 100 的事件，就必须暂停并查找缺失事件，不能直接跳到 101。

- **sequenceId** 表示事件在某个定序流中的位置；它回答“先处理哪个”。不必假设数据库自增号没有空洞，使用前驱指针或明确定义连续性。
- **requestId** 标识一次业务意图；它回答“是不是同一笔请求重试”。同一个 ID 换了金额或其他关键参数，应拒绝冲突，不能当成成功的重复请求。
- **消费游标**记录消费者已完成的位置；要与业务结果协调提交，否则崩溃可能造成重复处理或漏处理。

## 动手：观察乱序、重放和重复请求

将下列代码保存为 `SequenceDemo.java`，使用 JDK 17：

```java
import java.util.HashMap;
import java.util.Map;
import java.util.logging.Logger;

public class SequenceDemo {
    private static final Logger logger = Logger.getLogger(SequenceDemo.class.getName());
    record Event(long id, long previousId, String requestId, int delta) {}
    static class Consumer {
        private long lastId = 0;
        private int balance = 100;
        private final Map<String, Integer> applied = new HashMap<>();

        String accept(Event event) {
            /* ========================================================================
             * 步骤1：检查事件并更新本进程状态
             * 数据源：带序号的事件和内存中的处理记录
             * 操作：1) 校验顺序及重复请求 2) 更新余额和游标
             * ======================================================================== */
            logger.info("开始检查事件");
            // 1.1 已处理的序号不再执行；缺口时停止，等待补齐
            if (event.id() <= lastId) {
                logger.info("忽略旧事件");
                return "old";
            }
            if (event.previousId() != lastId || event.id() <= event.previousId()) {
                logger.info("检测到顺序缺口");
                return "gap";
            }
            // 1.2 相同请求号必须对应相同内容，避免重复产生业务效果
            Integer priorDelta = applied.get(event.requestId());
            if (priorDelta != null && priorDelta.intValue() != event.delta()) {
                logger.info("请求号与内容冲突");
                return "conflict";
            }
            if (priorDelta == null) {
                balance = Math.addExact(balance, event.delta());
                applied.put(event.requestId(), event.delta());
            }
            lastId = event.id();
            logger.info("事件处理结束");
            return priorDelta == null ? "applied" : "duplicate-request";
        }
    }
    public static void main(String[] args) {
        /* ========================================================================
         * 步骤1：演示顺序检查与请求去重
         * 数据源：固定事件序列
         * 操作：1) 故意乱序投递 2) 补齐后重复提交同一请求
         * ======================================================================== */
        logger.info("开始事件演示");
        // 1.1 缺口事件先拒绝，随后补齐并重放
        Consumer consumer = new Consumer();
        Event first = new Event(1, 0, "r1", -10);
        Event second = new Event(2, 1, "r2", 5);
        System.out.println("先到2=" + consumer.accept(second));
        System.out.println("处理1=" + consumer.accept(first));
        System.out.println("重放2=" + consumer.accept(second));
        System.out.println("重放1=" + consumer.accept(first));
        System.out.println("请求重复=" + consumer.accept(new Event(3, 2, "r2", 5)));
        System.out.println("冲突=" + consumer.accept(new Event(4, 3, "r2", 7)));
        System.out.println("余额=" + consumer.balance + ", 游标=" + consumer.lastId);
        logger.info("事件演示结束");
    }
}
```

```powershell
javac -encoding UTF-8 --release 17 SequenceDemo.java
java -Dfile.encoding=UTF-8 SequenceDemo
```

PowerShell 中若参数被拆开，可写成 `java '-Dfile.encoding=UTF-8' SequenceDemo`。标准输出如下，日志时间与位置可能不同：

```text
先到2=gap
处理1=applied
重放2=applied
重放1=old
请求重复=duplicate-request
冲突=conflict
余额=95, 游标=3
```

初始余额为 100。事件 1 扣 10，事件 2 加 5；事件 3 使用同一个请求号和金额，因此推进事件游标但不再加钱。事件 4 复用请求号却改变金额，报冲突并保持游标 3。此示例已用 JDK 17 编译并核对输出。

**示例边界**：这是单线程、单进程的内存演示。它假定上游不会用相同事件序号发送不同内容；`id <= lastId` 只表示旧序号，不能靠它验证历史事件内容。示例没有持久化、真实消息队列、并发控制、重放服务或故障恢复；金额用整数仅为说明状态变化，不是货币模型。

## 从演示走向可靠处理

1. **请求去重**：把请求 ID、关键参数摘要和处理结果持久化，用唯一约束处理并发重复提交；确定重试窗口和记录保留时间。
2. **持久化顺序**：定序器持久化接受的事件及其顺序。写入成功但通知下游前崩溃时，下游应能从可靠事件记录恢复；发布可以配合 outbox，不能只靠内存缓存。
3. **原子提交结果与游标**：如果业务更新和消费进度在同一数据库，可在一个事务中写入；不在同一事务边界时，要设计幂等、重试与对账。先写业务再记游标可能重复；先记游标再写业务可能漏处理。
4. **发现缺口**：事件前驱与当前游标不一致时停止该有序流，告警并从权威事件存储补齐；补齐失败不能悄悄跳过。确认前驱属于同一分区或同一顺序域。
5. **恢复**：从可信快照恢复状态后，从快照记录的位置开始重放；校验快照版本、输入顺序和状态一致性，并演练快照损坏和事件缺失。
6. **主备切换**：单纯有递增号不保证多个定序器永远只有一个有效写入者；需要可靠领导者选举、任期或栅栏令牌，防止旧主恢复后继续写入。

## 传递语义的边界

- **最多一次**：不保证重试，可能丢失，但不会因重试重复投递。
- **至少一次**：满足相应持久化与重试前提时可避免静默丢失，但可能重复，消费者仍要幂等。
- **恰好一次**：必须说清作用范围。Kafka 可在特定条件下将 Kafka 输入位点和 Kafka 输出事务协调起来；写入外部数据库或调用支付接口时，还需要与外部状态协调。教程称“任何消息系统都不能实现恰好一次”过于绝对，不能推导为端到端业务天然只生效一次。

## 自测

1. 重试请求使用新 requestId 会怎样？相同 requestId 换金额又会怎样？
2. 收到事件 101、当前游标为 98，能否直接处理？如何恢复？
3. 业务写库成功但游标保存前崩溃，恢复时可能发生什么？
4. 为什么 Kafka 分区内的顺序不等于多个分区之间的全局顺序？
