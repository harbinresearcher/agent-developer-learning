**笔记：算法效率评估**

算法先要“算对”，再比较“谁更快、更省内存”。

```
┌──────────┬────────────────────┬──────────────────────┐
│ 维度     │ 时间效率           │ 空间效率             │
├──────────┼────────────────────┼──────────────────────┤
│ 衡量对象 │ 运行耗时           │ 额外占用的内存       │
│ 常见问题 │ 数据大时会不会超时 │ 数据大时会不会爆内存 │
└──────────┴────────────────────┴──────────────────────┘
```

```
[评估算法] ──┬── 实际测试 ── 跑代码，测时间和内存
              └── 理论估算 ── 分析输入规模增大后的增长趋势
```

1. 实际测试：结果真实，但不够稳定

直接在机器上运行算法 A、B，记录耗时和内存。

它会受两个因素影响：

- 环境不同：CPU 核数、内存性能、编程语言、运行时状态都会影响结果。
- 数据规模不同：小数据下 A 可能更快；数据变大后，B 可能反超。

所以一次测试只能说明：**这个环境、这批数据下的表现**，不能直接证明算法本身更优。

2. 理论估算：复杂度分析

复杂度分析研究的不是“跑了 0.3 秒”，而是：

> 输入规模 `n` 变大时，时间和空间增长得多快。

```
n 从 1,000 增至 1,000,000

O(n)   ：工作量约增 1,000 倍
O(n²)  ：工作量约增 1,000,000 倍
```

因此复杂度分析能在不运行代码时预判：一个方案在大数据量下是否会失控。

```
┌────────────┬───────────────────────┬──────────────────┐
│ 方法       │ 能回答什么             │ 主要局限         │
├────────────┼───────────────────────┼──────────────────┤
│ 实际测试   │ 当前机器上实际跑多快   │ 受环境和样本影响 │
│ 复杂度分析 │ 数据变大后谁增长更慢   │ 不给具体秒数     │
└────────────┴───────────────────────┴──────────────────┘
```

3. 做题时的固定判断

```
先保证结果正确
↓
估算时间复杂度：数据量增大后会不会超时？
↓
估算空间复杂度：额外数组、递归、哈希表会不会超内存？
↓
再用实际测试验证常数、实现细节和真实数据表现
```

核心：复杂度不是为了算精确耗时，而是为了比较算法面对大规模数据时的增长趋势。之后学数组、链表、排序、搜索时，都要同时问：**快不快，省不省内存。**
